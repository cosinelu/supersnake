# 游戏设计：模式、规则与数值

> 读者：人类玩家/策划 + AI Agent。
> 本文是**玩法规则的唯一权威描述**；所有数值的真源是 `js/config.js`（逐项有注释），
> 本文只写规则与语义，改动数值请去 config.js 并同步本文对应描述。
> 联机实现细节（协议/同步模型）见 `docs/architecture/01-online-multiplayer.md`。

---

## 1. 一句话玩法

贪吃蛇的走位 + 祖玛（Zuma）的消除：自由方向游动，吃到色块**从头部插入**蛇身，
凑齐 **4 个相邻同色节**即消除得分。撞墙/撞蛇即死。尾巴永远有 1 节消不掉的「尾巴节」。

美术：蜡笔手绘风（纸色底 + 深色描边），8 色蜡笔调色板。

## 2. 四个模式的区别（核心速查表）

| | 闯关模式 | 无尽模式 | AI对战（本地） | 在线对战（联机） |
|---|---|---|---|---|
| 入口按钮 | 「闯关模式」 | 「无尽模式」 | 「AI对战」 | 「在线对战」 |
| 对手 | 无 | 无 | 3~14 条 AI 蛇（动态增长） | 2~4 名真人 + AI 补位 |
| 地图 | 随关递增（L1 1500×1000 → L10 4800×3200） | 3600×2400 | 4200×2800 | 4200×2800（同 AI对战） |
| 目标 | 达到本关目标分 → 过关，共 10 关 | 活下去刷最高分 | 活到最后 / 刷最高分 | 活到最后（≤1 名真人存活）或 5 分钟到时按总分 |
| 彩色星道具 | 不出现 | 不出现 | **出现**（+20% 总分抢夺） | **出现**（同左） |
| 需要服务器 | 否 | 否 | 否 | **是**（服务器权威模拟） |
| 结算依据 | 过关/撞死 | 最高分 | 名次 + 淘汰/击杀统计 | 名次 + 掉线判负 |
| 代码入口 | `game.js startLevel` | `game.js startEndless` | `game.js startMulti` → `multiplayer.js`（本地编排） | `game.js startOnline` → `net/onlineMatch.js`（客户端）+ `server/`（权威端） |

> 历史说明：「AI对战」在 v3.0 之前叫「多人对战」（容易和在线对战混淆，故改名）。
> 代码内部模式标识仍为 `multi`；`game.online` 非空表示该局是联机局。

## 3. 通用规则（四模式共享）

### 3.1 移动与碰撞
- 自由方向连续移动（非网格），转向速率上限 `TURN_RATE`；速度 = 基础 + 长度加成（每节 +2.5px/s），无尽模式另随时间提速。
- **撞墙/撞边界 → 立即死亡**；撞到自己身体不致死（见 3.4 自吃重组）。
- 边界墙 44px 纯视觉加厚；地图内每隔 9 秒动态新增一段障碍墙（避开所有活蛇，上限 28 段）。

### 3.2 吃色与消除
- 吃普通色块：该颜色一节**插入蛇头**（祖玛式一端推入）。
- **相邻同色 ≥4 节 → 消除**，基础分 = 节数 × `ELIM_SCORE`(10)。
- **连锁**：一次消除后新相邻的同色段 ≥4 会连续触发，分数 ×连锁层数。
- **连击**：2400ms 窗口内连续触发消除，倍率逐次 +1，封顶 ×5。
- **万能色节**（白底星标）：通配任意颜色，可桥接不同色段凑连。
- **长度保底**：任何消除或消除类道具（消色、后 3 消色、随机消）导致存活蛇的颜色节不足 3 节时，随机补至 4 块已解锁颜色砖继续。存活蛇不得出现 0 节颜色体；即使收到异常/降级快照，渲染层也必须保留可辨识的带眼睛头部，不能把唯一节点误画成尾巴。

### 3.3 尾巴节
- 每条蛇末尾恒有 1 节深色小尾鳍：**不参与消除判定、不会被消除/咬断移除、不占保底计数**。出生 = 5 颜色节 + 1 尾巴节 = 总长 6。

### 3.4 自吃重组
- 蛇头碰到**自己**身体时：从身体咬下一节补到头部（总长不变），制造凑连机会；冷却 380ms。

### 3.5 颜色解锁
- 调色板 8 色（红蓝绿橙紫黄青粉），开局解锁前 4 色。
- 闯关：每 2 关 +1 色（L9 起 8 色全解）；无尽：每存活 45 秒 +1 色；多人/联机：同无尽节奏。

### 3.6 计分
```
总分 = 存活分（1 分/秒） + 消除分（ELIM_SCORE × 连锁 × 连击 + 道具附加分） + 彩色星加成（多人局）
```

### 3.7 输入（摇杆 / 键盘）

- **键盘优先于摇杆**：方向键 / WASD，支持组合键（8 方向）；无按键时才读摇杆。
- **摇杆 = 屏幕左下角固定底座**，拖动方向即目标角（不量化），死区 `DEAD_ZONE`=16px。

**多点触控规则（v3.0.2 修正）**：早期实现是「单指独占锁」——`onTouchStart` 遇
`active` 直接 return、`onTouchMove` 要求 `id === touchId`。这会导致一类**输入永久卡死**：

| 触发场景 | 后果 |
|---|---|
| 手指 A 按着，手指 B 再触屏，然后抬起 A | B 仍在屏上却永不被响应，必须全部离屏重按 |
| 倒计时（`matching` 态）就按住手指，开局后直接拖 | 该次按下走了按钮分支，摇杆从未激活 → 整局锁死 |
| `matched` 时代码强制 `onTouchEnd` 重置摇杆 | 代码态与手指物理态脱钩，后续 move 全部失效 |

三者根因相同：**摇杆的「激活态」与手指的真实在屏状态会脱同步，且无自愈机制**。
放大器是 `onlineMatch.update` 的 `if (ang !== null && selfAlive)` —— 角度为 null 就
整帧不上行，服务器沿用旧角度让蛇直行，玩家感受为「蛇不听话，一直往前撞」。

**现行规则**：
1. **任意在屏手指均可接管摇杆**：`onTouchMove` 不再要求 id 匹配；未激活时收到 move
   即视为按下（自动 latch）。
2. **只有「当前接管的那根手指」抬起才释放**；其它手指抬起不影响。
3. **`play` 态入场时若已有触点**，用该触点立即 latch（覆盖倒计时按住的场景）。
4. 摇杆状态由「在屏触点集合」驱动，集合空才真正清零，避免代码态与物理态脱钩。

### 3.8 屏幕适配（横屏 / 竖屏）

`Game.layout()` 是布局的唯一权威来源，按朝向分两种形态（`portrait = H > W * 1.05`，
1.05 余量避免近正方时反复抖动）：

| 朝向 | HUD 面板 | 可玩区 |
|---|---|---|
| 横屏 | 右侧竖条，宽 = `clamp(W*0.19, 148, 230)`（窄屏压到 `0.24 / [110,148]`） | 占满高度 |
| 竖屏 | **顶部横条**，高 = `clamp(H*0.20, 132, 200)`（极端矮屏封顶 `H*0.34`） | **占满宽度** |

竖屏若沿用右侧竖条，面板会吃掉近半屏宽、可玩区退化成窄条，故改为顶部横条。
竖屏 HUD 横向分三栏：左（标题/模式/分数/速度）、中（目标或最高分 + 已解锁颜色单行 8 格
+ 排行榜两列最多 4 行）、右（正方形小地图）。

**返回值契约**：`viewX/viewY/viewW/viewH`（视口矩形）是世界渲染与相机的唯一依据；
`panelX/panelY/panelW/panelH` 为面板矩形；`areaW` 保留为 `viewW` 的兼容别名。
不变量：视口与面板恰好铺满屏幕、互不重叠、可玩区 > 屏幕对应边的 60%。

**其它适配点**：
- 摇杆底座随朝向调整：竖屏半径 62px / 边距 42px（横屏 52 / 30），并避让安全区。
- 安全区：`index.html` 把 `env(safe-area-inset-*)` 暴露为 CSS 变量，
  `Game.safeInsets()` 读取计算样式（JS 无法直接取 `env()`），非浏览器环境回退全 0。
- 重布局触发：`resize` + `orientationchange`（延迟 80ms/300ms 二次校正，旋转动画期间
  尺寸未稳定）+ `visualViewport.resize`（地址栏收起/展开时 `innerHeight` 未必及时更新）。
- **不做全屏**：Fullscreen API 必须用户手势触发，且 iPhone 上的 Safari 不支持；
  维持普通页面模式，靠上述适配保证观感。

#### 3.8.1 矮屏（手机横屏）纵向溢出治理（v3.0.3）

手机横屏可视高度只有 ~360~390px（还要再减浏览器工具栏），两处按**固定像素纵向堆叠**
的布局会溢出屏幕底部，且 canvas 没有滚动条、拖也拖不动：

| 问题 | 实测溢出 | 根因 |
|---|---|---|
| 右侧 HUD 小地图被切掉一截 | 844×390 溢 70px；800×360 溢 95px | `mapTop` 由「标题+分数+排行榜+颜色格」逐段累加得出，累加值与屏高无关 |
| 菜单 5 个按钮下面几个看不到 | 844×390 溢 73px；800×360 溢 91px | 按钮从 `H*0.40` 起、每个占 `54+16`px，5 个共需 ~340px |

**治理原则：一切纵向布局必须由「可用高度」反推，不允许固定像素堆叠溢出。**

1. **小地图改为「下对齐 + 尺寸自适应」**：先算出小地图可用高度
   `avail = H - mapTop - bottomReserve`，宽度取 `min(pw-28, avail / 地图宽高比)`，
   保证整幅小地图（含边框）落在面板内；宽度富余时仍按原宽显示，不放大。
   矮屏下小地图自动变小而**不再被裁切**。
2. **菜单按钮按可用高度自适应**：总需求高 = `n*bh + (n-1)*gap`，
   若超过可用高度则**等比压缩** `bh`/`gap`（下限 `bh=34`、`gap=6`），
   并把整组按钮**垂直居中**于可用区而非从 `H*0.40` 硬起步。
   仍放不下时（极端矮屏）才启用兜底：缩到下限并允许贴边。
   **不采用拖动滚动**——canvas 手势与摇杆/按钮冲突，且用户预期是「一屏看全」。
3. 同一套「可用高度 → 自适应」规则也应用于关卡选择页与结算页按钮组。

回归测试：`test/net/layout.test.js` 增加矮屏用例，断言
**所有 UI 按钮与小地图完全落在屏幕内**（这是本节的核心不变量）。

#### 3.8.2 横屏改用横向布局（v3.0.4）

§3.8.1 只做了「纵向压缩」，治症不治本 —— 压缩后按钮虽在屏内，却**盖住了标题下方的
蛇动画、副标题与底部信息**；结算记分牌压到 `rowH` 下限 24px 后卡片仍需 354px，
在 360~390px 的横屏上照样超出。**矮屏的正解是利用富余的横向空间，而不是继续挤压纵向。**

判定口径复用 `layout().portrait`，另加**矮屏**判定：`H < 460`（真机横屏都落在此区间）。

| 页面 | 横屏（矮屏）布局 | 竖屏 / 桌面 |
|---|---|---|
| 主菜单按钮 | **两列**（左 3 右 2），整组居中于标题与底部信息之间 | 单列 5 个 |
| 结算记分牌 | 统计项**两列 × 4 行**，卡片变宽变矮 | 单列 8 行 |

**主菜单两列规则**：
- 列数由可用高度决定：单列放不下（`n*bh + (n-1)*gap > avail`）时切两列，
  左列 `ceil(n/2)` 个、右列其余；列间距 24px，两列整体水平居中。
- 纵向可用区 = 标题下方（含蛇动画轨道 `H*0.22 + 52*0.95`）到底部信息之上
  （`H*0.89 - 12`），**不再侵占动画与文字的位置**。
- 两列后每列最多 3 个按钮，54px 原始高度即可放下，**不需要再压缩**。

**结算记分牌两列规则**：
- 8 项统计拆成左右各 4 行，卡片宽度放宽到 `min(560, W*0.86)`，
  高度随之降到约 `padV*2 + titleH + 4*rowH + footH`。
- 卡片底边必须停在按钮上方 20px 以上；仍不够时才压缩 `rowH`。

核心不变量（回归断言）：**任意尺寸下，菜单按钮不与蛇动画/副标题/底部信息重叠，
结算卡片完全落在屏内且不压按钮。**

实测效果（v3.0.4）：

| 尺寸 | 菜单 | 结算卡片 |
|---|---|---|
| 844×390 | 两列，按钮 50px，区间 156~332（动画 135 / 底部信息 347 之间） | 两列 560×298，距按钮 30px |
| 800×360 | 两列，按钮 44px，区间 151~305 | 两列 560×276，距按钮 26px |
| 1280×720 | 单列 54px（无回归） | 单列 440×434（无回归） |
| 390×844（竖屏） | 单列 54px | 单列 242×434 |

结算按钮在矮屏改为**贴底**（原 `H*0.87` 会把卡片可用区压掉太多），矮屏按钮高 42px。

回归测试：`test/net/layout.test.js` T7（98 → **156 条断言**）。

#### 3.8.3 真实截图复验推翻「压缩式适配」（v3.0.5）

§3.8.1 / §3.8.2 的断言全绿（617 项），但**用无头浏览器按真机尺寸截图后，观感是坏的**。

> **方法论教训（本节最重要的一条）：「元素在屏内」≠「元素互不重叠」。**
> 前两轮的断言只校验了元素不出屏，导致所有**遮挡类**缺陷被漏过。
> Canvas UI 没有 DOM 可查、没有 CSS 盒模型可验，**几何断言与像素截图缺一不可**。

截图暴露的三处缺陷：

| 界面 | 缺陷 | 量化 |
|---|---|---|
| 横屏菜单 | 右列比左列**下沉半格**（两列起点不同）→ 视觉错位；副标题与蛇动画**重叠成团**；两列中间留白过大 | — |
| 竖屏 HUD 顶栏 | 三栏**硬编码固定像素**，窄屏中栏被挤爆 | 390px 宽下中栏仅 122px，颜色格需 168px |
| 结算卡片 | 按**整屏宽**居中，无视右侧 HUD 存在 → 直接盖住面板 | 844×390 压 18px；800×360 压 32px |

**治理原则（三条，逐层递进）：**

1. **横屏用横向分栏，不是把内容挤进纵向。**
2. **一切坐标由「可用区」推导，禁止写死固定像素分栏。**
3. **重排必须全局派发，各界面各自响应，不允许在 draw 里临时判断朝向。**

##### A. 主菜单：横屏左右分栏

| 区域 | 横屏（矮屏 `H < 460`） | 竖屏 / 桌面 |
|---|---|---|
| 品牌区 | **左半区**：标题、蛇动画轨道、副标题、底部统计 | 顶部（标题）+ 底部（统计） |
| 操作区 | **右半区**：单列 5 按钮，整组垂直居中 | 屏幕中部单列 5 按钮 |

左右分栏后品牌区与按钮区**不再共享纵向空间**，重叠在结构上不可能发生
（§3.8.2 的两列方案仍与标题带争夺纵向空间，是错位与遮挡的根源）。
分界线 `splitX = W * 0.46`，按钮区在 `[splitX, W - pad]` 内水平居中。

顺带修复：竖屏副标题过长会被右边缘截断，改为按可用宽度**自动降级**
（先缩字号，仍不够则丢弃末段短语）。

##### B. 结算记分牌：在「对局区」内居中

卡片的水平中心与宽度上限一律取自 `layout()` 的**视口矩形**（`viewX/viewW`），
不再用整屏 `W/2`。横屏时视口已排除右侧 HUD 面板，竖屏时排除顶部 HUD 高度，
因此卡片**结构上不可能压到面板**。HUD 保留在结算画面上（仍可看最终排行榜与小地图）。

##### C. 竖屏 HUD 顶栏：三栏改三行流式

固定三栏（左 132 + 中 + 右 96）在 390px 宽下数学上放不下。改为：

| 行 | 内容 | 分配方式 |
|---|---|---|
| 1 | 模式 + 大号分数 + 排位 | 左起顺排，右端固定正方形小地图 |
| 2 | 已解锁颜色格 + 速度 | 由第 1 行剩余宽度推导起点 |
| 3 | 排行榜横排（不足则换行） | 占满除小地图外的全宽 |

所有 x 坐标由**剩余可用宽度**推导；空间不足时按优先级丢弃：速度 → 颜色格 → 排行榜尾行。

##### D. `layoutBus`：全局重排派发

原先各界面在 `draw` 里临时判断朝向，旋转后**缓存不失效**（按钮矩形、测量值仍是旧的）。
现改为事件总线：

```
resize / orientationchange / visualViewport.resize
        → CS.layoutBus.emit('relayout', {W, H, portrait, short})
        → Game      清 _layoutCache、重建 uiButtons、重设摇杆底座、重新钳制相机
        → Renderer  清文本测量与面板几何缓存
```

订阅者用 `CS.layoutBus.on('relayout', fn)` 注册。`layoutBus` **DOM 无关**
（不引用 `window`/`document`），可在 node 测试里直接 `emit` 验证订阅者反应。

核心不变量（回归断言，**替代**§3.8.2 的「在屏内」口径）：

> 任意尺寸下，**任意两个 UI 元素的矩形不相交**——
> 按钮之间、按钮与品牌区、按钮与底部信息、结算卡片与 HUD 面板、HUD 内部各区块之间。

回归测试：`test/net/layout.test.js` T8（重叠矩阵）+ T9（`layoutBus` 派发与缓存失效）。

## 4. AI对战（本地）细则

- **编制**：开局 3 条 AI，每存活 25 秒 +1 条，封顶 14 条；AI 被淘汰后 3~5 秒重生补编。
- **AI 决策**（`js/ai.js`，加权转向）：每帧评估 24 个候选方向 = 寻食吸引（偏好同色/凑连）− 撞墙/撞蛇/自卷/头对头惩罚 + 惯性 + 游走噪声。
- **性格差异**：每条 AI 有随机速度档（130~170px/s）与性格参数（贪食/谨慎）；早期 AI 莽/怂差异大，后期（智力随时间 0→1 渐变）更均衡聪明。
- **咬断机制**：头撞其他蛇身体 → 撞者死亡，被撞者被咬掉「离撞者头最近的一节」；被咬后不足 3 节 → 直接淘汰并计撞者 1 击杀。头对头相撞 → 双双淘汰。
- **尸体掉落**：死蛇每隔 2 节掉 1 个色块（≈50% 的节）+ 必掉 1 个随机道具（每 10 节再 +1 个）。
- **彩色星**：见 §5 道具表，仅多人/联机出现。
- **HUD**：右侧实时排行榜（按节数降序），头顶昵称标签（玩家为「我」，AI 从昵称池取不重复的名字）。

## 5. 在线对战（联机）细则

与 AI对战同地图同规则，差异全部来自「服务器权威 + 真人对手」：

### 5.1 匹配
- 队列满 4 名真人立即开局；队首等待超 20 秒且 ≥1 名真人 → 以现有真人 + AI 补位开局（**一个人也能开局**）。
- 匹配中可取消；开局倒计时 3 秒。

### 5.2 权威模型（客户端不可信）
- 服务器 30Hz 固定步长模拟，15Hz 广播快照；客户端只上行转向输入（30Hz 节流）。
- 本机蛇 = 客户端预测 + 快照软校正；他机蛇 = 120ms 插值。
- **掉线 = 判负**，不支持重连；本人死亡立即收到结算（对手继续）。

### 5.3 结算
- 多真人局：存活真人 ≤1 → 存活者胜；单真人局：本人死亡 → 结算（AI 存活不影响）。
- 或 5 分钟对局上限到时 → 按总分排名。
- 排行榜：存活优先，其后按总分降序。

### 5.4 昵称规则
- 昵称存于 localStorage `crayon_snake_web_nick`；首次缺省生成「我+4 位随机数」，最长 12 字。
- **同局真人昵称由服务器去重**：同名依次追加 `·2` `·3`（超长先截断基部）——同一浏览器多标签页共享 localStorage 时昵称必然相同，靠服务器去重保证名牌可区分（`server/matchmaker.js _dedupeNames`）。
- **AI 不与真人撞名**：真人昵称注册进 `usedNames`，AI 取名避让；真人淘汰后其名字整局保留（`js/multiplayer.js addPlayer/kill`）。
- 回归测试：`test/net/nick.test.js`。

## 6. 道具系统

稀有度 4 档（边框：彩虹金 > 橙 > 紫 > 蓝）。特殊道具出现概率随存活时间从 12% 线性爬到 42%（180 秒到顶）。

| 道具 | 稀有度 | 效果 | 备注 |
|---|---|---|---|
| 彩色星 | 彩色·抢夺 | 玩家吃到：当前总分立即 +20%（可叠加）；AI 吃到只消耗不加分 | **仅多人/联机**；开局 18s 首现，场上最多 1 颗，被吃/42s 超时后 32s 再现；全屏播报 + 小地图涟漪，AI 高优先抢 |
| 万能色 | 强 | 通配任意颜色，桥接不同色段凑 4 连 | |
| 炸弹 | 强 | 清除蛇身所有 ≥2 节的连续同色段 | 每节额外 +8 分 |
| 消色 | 强 | 消除蛇身全部指定颜色节（不管位置/连续性） | 每节额外 +6 分 |
| 流星砖块 | 中 | 从地图边缘直线飞入，命中蛇身把该色注入中段 | 每 6.5s 一颗，同屏 ≤3 |
| 后三消色 | 中 | 只消除指定颜色最靠尾的 3 节 | 每节额外 +5 分 |
| 随机消 3 | 中 | 随机移除 3 节 | |
| 减速 | 弱 | 4 秒内速度 ×0.6 | 防御型喘息 |
| 随机消 1 / 2 | 弱 | 随机移除 1 / 2 节 | |
| 普通色块 | 无 | 头部插入 1 节该颜色 | 基础食物 |

刷新权重与全部参数见 `js/config.js`（`ITEM_WEIGHTS` / `GRAB_*` / `METEOR_*`）。
