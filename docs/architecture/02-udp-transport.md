# UDP 传输层与二进制协议（v3.1）

> 状态：设计定稿，待实现
> 上游设计：`docs/architecture/01-online-multiplayer.md`（同步模型与权威判定，本文不重复）
> 本文只描述**传输层与线上编码**的变更，游戏逻辑、判定归属、房间生命周期一律不变。

---

## 1. 为什么要改

现状 WebSocket 走 TCP。弱网下丢一个 MSS 分片会触发**队头阻塞**：后续已到达的数据被压在内核缓冲里等重传，
表现为周期性卡顿。而本项目的同步语义**根本不需要可靠传输**：

| 方向 | 内容 | 幂等性 | 丢包后果 |
|---|---|---|---|
| 上行 | 绝对朝向角 `a`（不是增量 Δ） | **幂等**：新包完全覆盖旧包 | 33ms 后新包自动补上，**无累积误差** |
| 下行 | 全量世界状态快照 | **幂等**：新状态覆盖旧状态 | 下一帧就是完整的新状态 |

两端都幂等 ⇒ **旧数据零信息价值** ⇒ 重传是纯浪费。
所以采用**纯不可靠 UDP + 冗余副本**：不要 ACK、不要重传队列、不要拥塞窗口、不要 KCP。

> **前提约束（必须成立，改动时不可破坏）**：
> 上行必须保持「绝对量」语义。若将来新增**一次性离散操作**（如技能按钮），
> 那类指令**不可替代**，必须单独设计（走 TCP，或上行携带前 N 帧的技能事件做补发）。
> 见 §7.3。

### 1.1 关键前置发现：不瘦身则 UDP 不可用

实测后期最坏快照（18 蛇 × 25 节 + 168 色块）= **19662 字节**，
UDP 发出会被切成 **14 个 IP 分片**：

```
以太网 MTU                     1500 字节
减 IP 头 20                    1480 字节/片（须为 8 的倍数）
UDP 数据报 = 19662 + 8(UDP头) = 19670 字节
分片数 = ceil(19670 / 1480)  = 14 片
```

**IP 分片重组在内核完成，缺任何一片则整组丢弃**，应用层 `recvfrom()` 收不到任何东西（连残片都没有）。
这造成丢包放大：

| 单片丢包率 | 14 片全到 | 整帧报废 |
|---|---|---|
| 0.5% | 93.2% | 6.8% |
| 2% | 75.4% | **24.6%** |
| 5% | 48.8% | **51.2%** |

1 片的包丢 2% 就是 2%，14 片的包丢 2% 变成 24.6% —— **12 倍恶化，比 TCP 还糟**。

结论：**必须先把单帧压进一个 datagram（≤1472 字节），UDP 方案才成立。**

## 2. 下行二进制编码

### 2.1 节心用「方向角 + 间距」而非绝对坐标（核心优化）

实测相邻节心间距分布（1600 样本，含急转弯）：

```
25~30px : 99.3%      范围 25.92 ~ 30.00 px
30~35px :  0.7%      （SEG_SPACING = 30，急转时弦长压缩到 26）
```

间距近似恒定 ⇒ 主体只传**每节相对上一节的方向角**（uint8，2π/256 = 1.4°）。

**但有两个坑，实测才暴露出来，缺一个都会让蛇散架：**

#### 坑 1：误差沿链单调累积 → 必须插绝对锚点

角度量化误差每节约 0.7px，沿链累加。实测无锚点时：

| 蛇长 | 尾部误差 |
|---|---|
| 25 节 | 5.4px（可接受）|
| 45 节 | 51.3px（明显歪斜）|
| 71 节 | **838px（整条蛇散架）** |

⇒ **每 `ANCHOR_EVERY = 16` 节插入一次绝对坐标**（uint16 × 2），误差清零。

#### 坑 2：节心可能重叠 → 间距不能一律按 SEG_SPACING 外推

出生瞬间 / 轨迹弧长不足时，尾部节心会**全部堆在轨迹末点**（间距 0）。
若解码端一律按 30px 外推，会把重叠的尾巴甩出去（实测 **450px**）。

⇒ 间距偏离 `SEG_SPACING` 超过 `DIST_EPS = 1.0` 的节，
其「节号 + 间距」记录在角度序列之后的**异常表**里。

> 为什么用独立异常表而不是借角度的 bit0 做标志：借 bit0 会让角度精度从 1.4° 降到 2.8°，
> 实测节心误差从 1.76px 涨到 5.54px。

#### 参数选择依据

对「锚点间隔 4/6/8/12/16 × 间距策略 5 种」共 25 组配置做过扫描，
在「最大误差 < SEG_RADIUS/2」的可行解中取体积最小：

| 配置 | 25 节单蛇 | 最大误差 |
|---|---|---|
| **ANCHOR=16, EPS=1.0** | **73 B** | **3.94px** ← 采用 |
| ANCHOR=16, EPS=1.5 | 68 B | 4.92px |
| ANCHOR=16, EPS=3.0 | 59 B | 14.75px（散架）|
| ANCHOR=8, always | 83 B | 1.49px |

最终实测：**任意长度（10~120 节）最大误差 ≤5.3px**，SEG_RADIUS=13，肉眼不可见。

### 2.2 单蛇稳态帧结构

| 字段 | 字节 | 编码 | 说明 |
|---|---|---|---|
| `id` | 1 | uint8 | 实体 id（房内 ≤18 条）|
| `flags` | 1 | 位域 | bit0 alive / bit1 isPlayer / bit2 lite / bit3 bitten / bit4 slow |
| `x` | 2 | uint16 LE | 1px 精度（地图 4200×2800 < 65535）|
| `y` | 2 | uint16 LE | |
| `angle` | 1 | uint8 | `(a+π)/2π×255`，精度 1.4° |
| `speed` | 1 | uint8 | 4px/s 精度 |
| `segCount` | 1 | uint8 | 身体节数 |
| 角度序列 | N | uint8 × N | 每节方向角；每 16 节后追加 uint16×2 锚点 |
| 异常间距表 | 1+2M | count + [节号, 间距] × M | 仅偏离稳态的节（实测占比很低）|
| 颜色 | ⌈N/2⌉ | 4bit × N | 每字节两节 |

**固定 8 字节 + 每节约 1.6 字节。** 25 节蛇实测 **73 字节**（原 JSON 438 字节，6 倍）。

`lite` 标志位为 1 时 `segCount = 0`，只有头部信息，共 8 字节（见 §2.5 LOD）。

### 2.3 移出每帧的字段

以下字段**永不变或低频变**，从每帧移到 **1Hz 低频通道**（走 TCP，见 §4.2）：

- `nm` 昵称（20 B/蛇，整局不变）
- `kl` `es` `et` `ml` `sv` `mb` 计分类（83 B/蛇，HUD 与排行榜用，1Hz 足够）

### 2.4 色块增量同步

色块不能只传坐标和颜色：普通色块、特殊道具与多人彩色星都在同一个 `blocks` 集合中，
`kind` 决定碰撞效果和渲染；彩色星的 `color` 还是 `null`。遗漏这两项会把所有特殊道具
错误降级成普通红色色块。

**二进制色块 = 8 字节**：`id`2 + `x`2 + `y`2 + `c`1 + `kind`1。
`c=15` 专门表示 `null`；`kind` 用稳定枚举编码。`rarity` 与收集半径可由 `kind`
在客户端恢复，1Hz 全量校正仍携带完整语义作为可靠基线。

| 帧类型 | 频率 | 结构 | 典型体积 |
|---|---|---|---|
| **增量帧** | 每帧（30Hz） | `addCount`1 + N×8 + `delCount`1 + M×`id`2 | 24 字节（add 2 / del 3）|
| **全量校正** | **1Hz** | JSON 全量（含 `kind/rarity/radius`） | 约 1~2 KB |

全量校正**走 TCP**（低频、体积大、不能丢），用于修复客户端因漏收增量导致的偏差。
客户端收到全量后直接整体替换色块集合，再继续应用二进制 add/del。

#### 2.4.1 移动流星必须逐帧进入二进制快照

流星以约 140px/s 移动，不能塞进 1Hz meta（否则每次会跳约 140px）。协议 v3 把
`mid/x/y/vx/vy/color/phase/trail` 随加速快照发送；流星上限 3 颗、单颗最多约 37B，
增加的体积仍可由 `encSnapCapped()` 通过远端蛇 LOD 守住 1400B 硬上限。
`mid` 是整颗流星生命周期内稳定的服务端实体 id，客户端据此做跨快照关联；
没有它，多颗流星交叉/重生时只能靠位置猜测，轨迹可能接错。
客户端先把二进制长键对象规范化为 JSON snap 的 `sn/bl/mt` 短键结构，再交给
`RemoteMatch.applySnap()`；测试直接穿过这条真实消费链，不能只比较蛇字段名。

### 2.5 视野裁剪：三档 LOD

二进制化后 18 条蛇才 594 字节，视野裁剪从「必须」降级为「优化」。
采用三档而非简单的发/不发，**保证小地图永远有全部蛇的位置**：

| 档位 | 条件 | 内容 | 字节 |
|---|---|---|---|
| **完整** | 视口 1.4 倍范围内 | 头 + 全部节心角 | 8 + N |
| **精简**（`lite`） | 视口外 | 只有头部状态（供小地图定位） | 8 |
| **不发** | 已死亡且尸体已消失 | — | 0 |

本机玩家自己的蛇**永远完整档**，不受裁剪影响。

### 2.6 体积实测与硬约束

基线 18 蛇 × 25 节 + 168 色块（**实测值，非估算**）：

| 方案 | 体积 | 压缩比 | 分片 |
|---|---|---|---|
| S0 JSON 现状 | 19572 B | 1.0x | 14 片 |
| **S2 二进制 + 色块增量** | **1336 B** | **14.6x** | **1 片** |
| S3 再加视野裁剪（LOD） | ~600 B | ~32x | 1 片 |

极端场景（必须靠 LOD 降级）：

| 场景 | 全完整档 | encSnapCapped 后 |
|---|---|---|
| 18 蛇 × 71 节 | 3479 B | 降级后 ≤1400 B |
| 18 蛇 × 120 节 | 5883 B | 降级 15 条 → 1128 B |

因此设**硬约束兜底**，由 `binProtocol.encSnapCapped()` 实现：

> **组包时若体积 > 1400 字节，从最远的蛇开始降级为 `lite` 档，直到满足约束。**
> 本机玩家（entries[0]）**永不降级**。降级发生时应打点告警。
> 降级后仍保留全部蛇的头部位置，**小地图不缺人**。

> 实现要点：测试必须调用**正式的 `encSnapCapped`**，不能在测试里手写一遍降级循环 ——
> 手写副本会与实现脱钩（这个教训在 `layout.test.js` 上已经吃过一次：
> 实现改成视口驱动后测试仍用旧公式，却依然全绿）。

### 2.7 为什么不用 gzip

| 方案 | 体积 | 压缩比 | CPU |
|---|---|---|---|
| JSON + gzip(level 1) | 4452 B | 4.4x | 0.53 ms/次 |
| **二进制（无压缩）** | **632 B** | **31.1x** | ~0 |
| 二进制 + deflateRaw | 607 B | — | **比不压缩的 602 B 还大** |

三条否定理由：

1. **收益远不如二进制**：4.4x vs 31x
2. **CPU 不可接受**：30Hz × 18 人 × 5 房 = 2700 次/秒 × 0.53ms = **142% 单核**。
   且 LOD 裁剪后每人的包各不相同，无法复用一次压缩结果。
3. **二进制已接近熵极限**：再压反而增大（deflate 头部开销 > 可压缩冗余）。

## 3. 上行 Fragment 协议

### 3.1 结构（12 字节）

| 字段 | 字节 | 说明 |
|---|---|---|
| `magic` | 1 | 包类型标识，快速丢弃垃圾流量 |
| `token` | 4 | 会话令牌，**身份识别用**（见 §3.4）|
| `frameId` | 2 | 客户端帧号，uint16 |
| `angle` | 2 | uint16，`2π/65536`，精度 0.005° |
| `flags` | 1 | boost 等 |
| `crc16` | 2 | 校验（见 §3.5）|

对比现状 JSON 41 字节。30Hz × 3 副本 = **1.05 KB/s**（含 IP+UDP 头 28B 则 3.5 KB/s）。

### 3.2 frameId 语义

- **客户端自己的计数，各端不要求一致**，服务器只用它判先后。
- uint16 在 30Hz 下 **36.4 分钟**才环回；对局上限 5 分钟 = 9000 帧，**一局内绝不环回**。
- 服务器去重规则（与现有 `room.js:113-122` 语义一致，只换传输层）：
  ```
  frameId > lastFrameId + MAX_JUMP      → 异常跳变，丢弃
  frameId < lastFrameId 且回退幅度小     → 网络乱序，丢弃（后续更新的包会补上）
  frameId < lastFrameId 且回退幅度大     → 客户端重新计数，接受并重置基线
  否则                                   → 采纳，lastFrameId = frameId
  ```
  > 「大幅回退需重置基线」这条是既有教训：客户端重连后 frameId 归零而服务器基线停在旧值，
  > 会导致该玩家输入**永久**失效（表现为「怎么划都不动」且无法自行恢复）。

### 3.3 冗余副本必须时间打散（关键）

**丢包不是「按包」发生的，是「按时间段」发生的** —— 基站切换、路由缓冲溢出、信道竞争
都会持续 20~100ms，期间经过的所有包全丢。

3000 帧实测（"服务器未收到新指令的帧"占比）：

| 丢包形态 | x1 | x3 同时发 | **x3 打散** |
|---|---|---|---|
| 突发 30~80ms 长窗口 | 10.20% | 10.20% | **6.37%** |
| 突发 5~20ms 短窗口 | 7.90% | 7.90% | **0.23%** |
| 独立丢包 8% | 7.87% | 7.87% | **0.07%** |

**`x3 同时发` 与 `x1` 完全相同**（不是相近，是一模一样）—— 同一毫秒的副本在丢包窗口内**同生共死**。

**规则：一帧内按副本数均分间隔发送。**
`UDP_DUP = 3` 时，帧间隔 33ms → 偏移 `0 / 11 / 22ms`。
`UDP_DUP` 为配置项，偏移由 `frameIntervalMs / UDP_DUP × i` 推导，改份数无需改代码。

> 长窗口（>33ms）场景下改善有限（10.2% → 6.4%），因为三份都落在窗口内。
> 该场景真正的解法是缩小单帧体积（§2），而非增加副本。

### 3.4 会话令牌：身份识别，不是安全机制

**为什么需要**：UDP 无连接，源 `IP:Port` 在 NAT 重绑定 / 4G↔WiFi 切换时会变，
服务器需要稳定标识才知道包属于哪个玩家。这是**功能需求**。

**为什么不做 HMAC / 加密**：判定权 100% 在服务器，上行只有一个角度，没有任何声明性字段。
伪造别人的 input 只能让他的蛇转个向，**改不了血、改不了分、改不了判定**；
伪造下行给自己只影响本地显示，下一帧真快照就覆盖了。攻击面近乎为零，不值得引入密钥管理。

唯一真实威胁是往 UDP 端口灌垃圾流量（DoS），靠 `magic` 快速丢弃 + 每源限速即可。

### 3.5 CRC16：防损坏，不防伪造

UDP 头已有 16-bit checksum（漏检率 ≈ 0.0015%）。额外的 CRC16 用于覆盖
中间设备篡改与 checksum 漏检的残留错误。CRC32 实测单次 0.07μs，CRC16 更低，成本可忽略。

**明确认知：攻击者同样能算出正确 CRC，它不是安全机制。**

服务器三道校验，任一失败即静默丢弃：

1. `magic` 匹配 → 拒绝垃圾流量
2. `token` 匹配已知会话 → 身份识别
3. `crc16` 通过 且 `isFinite(angle)` 且 frameId 规则通过 → 拒绝损坏与非法值

## 4. 双通道架构

### 4.1 职责划分

```
TCP（WebSocket，保持现状，JSON 编码，不做任何额外处理）
  ├── join / cancel / queued / matched / start / over    连接与生命周期
  ├── event（消除 / 死亡 / 自碰 / 道具）                  ← 一次性离散信息，不可替代
  ├── 1Hz 低频通道：昵称、计分、排行榜                     ← §2.3 移出的字段
  ├── 1Hz 色块全量校正                                    ← §2.4
  └── UDP 不可用时的降级快照通道

UDP（二进制，冗余打散）
  ├── 上行 input Fragment（30Hz × UDP_DUP）
  └── 下行 snap 状态帧（30Hz × UDP_DUP）
```

**划分原则：UDP 传幂等的（丢了下一帧覆盖），TCP 传不可替代的（丢了没法补）。**

`over` / `matched` / `event` 属于后者 —— 没有「下一帧」来救，必须可靠。

### 4.2 为什么 TCP 保底继续用 JSON

保底通道的价值在于**足够简单、足够稳**。两套编码并存的代价是协议层多维护一份序列化，
但换来 TCP 路径零风险 —— 即使二进制编码有 bug，降级后仍能正常游戏。

### 4.3 连接建立与降级

```
1. TCP 先连上，完成 join / matched
2. 服务器在 matched 消息里下发 UDP / WebTransport offer
3. 客户端向加速端点发 hello(token)，服务器回 hello_ack（客户端严格校验长度/CRC/token）
4. 1.5s 内未收到合法 ack   → 客户端经 wss 发送 accel(on=0)，全程走 TCP
5. 对局中连续 500ms 无合法加速下行 → 经 wss 发送 accel(on=0)，服务器立即恢复 TCP 快照
6. 后台 hello 再次收到合法 ack → 经 wss 发送 accel(on=2)，进入 TCP + 加速双发探测
7. 客户端收到一帧完整、可解码的二进制 snap → 发送 accel(on=1)，停止 TCP 双发
```

**TCP 连接全程保留不断开，但“保留连接”本身不等于完成降级。** 服务端若只看历史
握手状态，单向下行异常时仍会把会话判为 ready 并抑制 TCP，客户端则已切到 TCP，
结果两边都不发预期快照。故暂停/恢复必须通过可靠的 wss 控制面显式同步。

恢复也不能只凭 7B `hello_ack`：小 ACK 可达不代表完整 datagram 可达。`mode=2`
探测期间两条下行同时保留，只有完整二进制快照到达才切回 `mode=1`。同时，
`lastRecvAt` 只能由通过长度/CRC/token 校验的 ACK 或成功解码的快照刷新；随机坏包
不能给通道“续命”。`udp.e2e.test.js` 覆盖“已激活 → 停滞 → TCP 恢复 → 双发探测 →
完整帧确认恢复”的真实 socket 闭环。

### 4.4 NAT 保活

UDP NAT 映射通常 30 秒无流量即失效。上行 30Hz 天然保活，
但**已死亡玩家 / 观战状态不发上行**，需要 **5 秒一次空 keepalive**。

## 5. 频率配置

### 5.1 三层频率互相独立

这是本项目网络分层的前提，四个频率各管各的，改一个不牵动其他：

| 层 | 频率 | 权威来源 | 说明 |
|---|---|---|---|
| 上行输入 | 30Hz 固定 | `onlineMatch.INPUT_INTERVAL_MS = 33` | 幂等绝对角度，12B/包，无理由随下行降频 |
| 服务器模拟 | 30Hz 固定 | `TICK_MS = 33` | 判定步长，**与发包频率解耦** |
| 下行快照（UDP / WebTransport） | 30Hz 可配 | `TICK_MS × SNAP_EVERY` | 二进制加速通道的带宽旋钮 |
| 下行快照（TCP / wss 保底） | 15Hz 可配 | `TICK_MS × TCP_SNAP_EVERY` | 全量 JSON；优先稳定与低带宽 |
| 客户端渲染 | 60Hz+ | `requestAnimationFrame` | 永不等网络；120Hz 屏就跑 120Hz |

| 配置项 | 默认 | 说明 |
|---|---|---|
| `TICK_MS` | 33 | 服务器模拟步长（30Hz），不变 |
| `SNAP_EVERY` | **1** | 加速通道每 N tick 广播一帧。1 = 30Hz，2 = 15Hz |
| `TCP_SNAP_EVERY` | **2** | TCP 保底每 N tick 广播一帧。默认 15Hz，避免 30Hz 全量 JSON + TCP 队头阻塞 |
| `UDP_DUP` | 3 | 冗余副本份数，1 = 关闭冗余。**可用环境变量覆盖**（`UDP_DUP=1` 起实例做 A/B 对照） |
| `LOWFREQ_MS` | 1000 | 低频通道与色块全量校正间隔 |

### 5.2 输入序号跨通道共享

TCP 与 UDP / WebTransport 只是同一条**逻辑输入流**的不同承载，必须共用一个单调
`seq/frameId`。`WsTransport.sendInput()` 每个 30Hz 逻辑输入只递增一次序号，再把同一个值
交给当前物理通道。服务端加速端点只负责副本去重，随后将该 `frameId` 原样交给
`Room.handleInput()` 并写入快照 `ack`。TCP 输入被房间采纳后还要经
`TransportHub.syncInputSeq()` 同步端点的去重基线，否则回落超过约 33 秒后，恢复的首个
加速序号会因前跳超过 `INPUT_MAX_SEQ_JUMP` 被持续拒绝。

不能让两条通道各自从 1 计数，也不能由服务端按收到的包数另造 `lastSeq+1`：玩家先走
少量加速输入再回落 TCP 时，较小的 TCP seq 会被误判为乱序，方向可能冻结直到追平
`INPUT_SEQ_RESET_GAP`。`udp.client.test.js` 与真实 socket E2E 分别守住客户端连续性和
服务端 ack 基线。

### 5.3 插值延迟按实际通道自适应

频率不再假定全连接一致。`matched` 同时下发 TCP 与加速通道的实际间隔；客户端初始按
TCP 的 66ms / 119ms 缓冲运行，WebTransport / 裸 UDP 真正收到二进制帧后切到
33ms / 70ms，若中途停滞回落 wss，则立即恢复到 66ms / 119ms。切换不改渲染层代码，
`interpolation.js:deriveDelay` 仍按当前实际间隔推导：

```
delayMs = snapIntervalMs × 1.5 + 20      // 钳制在 [50, 400]
capFrames = ceil(2000 / snapIntervalMs)  // 缓冲保留约 2 秒历史
```

- **1.5 倍间隔**：1 倍只是「刚好有前一帧」，插值系数 t≈0，
  任何抖动都会让渲染时刻越过最新帧、被钳制成卡顿；1.5 倍留半帧余量
- **+20ms 固定项**：网络抖动与快照频率无关，不该随提频一起缩水
- 15Hz(66ms) → **119ms**；30Hz(33ms) → **70ms**

> 119ms 与改造前的硬编码 120ms 实质等同 —— 这是刻意的：
> **提频改造不得改变提频前的行为**，否则回退 15Hz 时手感会变，
> 分不清是频率的差异还是公式跑偏。已写成断言。

**顺序不可颠倒：先自适应，再提频。** 但「频率更高」也不代表所有传输都应使用同一缓冲：
TCP 的可靠有序语义会在丢包重传时产生队头阻塞，多个 30Hz 全量 JSON 快照成批到达；
若仍按理想 33ms 推导 70ms 缓冲，渲染时刻会频繁越过最新帧并被钳住，表现为
「停一下、再跳一下」。因此 30Hz / 70ms 只用于 UDP / WebTransport，wss 保底恢复为
已经过长期验证的 15Hz / 119ms。这里不是把渲染绑到网络，而是为两种物理特性不同的
传输分别选择安全缓冲。

`capFrames` 同理不能写死帧数：固定 30 帧在 15Hz 是 2 秒历史、
30Hz 只剩 1 秒，提频等于悄悄砍掉一半窗口。

通道切换时还必须清空**到达统计基线**（`lastAt/lastTick`，不清累计样本）：
否则从加速通道回到 TCP 后，两个 TCP 快照之间横跨的正常加速时段会被误报为大量
“TCP 缺帧”和一次超长卡顿。

### 5.4 本机蛇不受插值延迟影响

插值只作用于**他人蛇与移动实体**。本机蛇走 `SelfPredictor` 预测 + 软校正，
操作到画面的延迟恒为 0，与 `SNAP_EVERY` 无关。

### 5.5 远端回放使用服务器 tick 时间线

`renderT = now - delayMs` 仍然成立，但快照括号必须放在 `tick × tickMs` 推导出的
权威时间线上，而不是本地 `Date.now()` 收包时刻。WSS 队头阻塞解除后，多个快照可能
同一毫秒批量到达；若按收包时刻回放，远端蛇会把等待期间的运动压缩到一两帧内，
玩家看到的就是「停一下、突然连跳」。二进制通道的 tick 是 uint16，TCP JSON 不截断；
客户端必须先展开成单调序号，保证 65535 → 0 与跨通道同 tick 双发都不会回滚。

锚点调整是不对称的：时延下降立即前锚；时延上升必须持续 `REMOTE_REANCHOR_MS`
才后锚。这样一次批量到达不会打乱节奏，持续高时延也不会让远端实体永远处在外推兜底。

缓冲耗尽后的兜底也分实体：

- 远端蛇：按最新 `speed/angle` 外推，并整体平移 `segPos`；
- 流星：按稳定 `mid` 关联后按 `vx/vy` 外推，并整体平移 `trail`；
- 超过 `REMOTE_EXTRAPOLATE_MS` 后停住，避免长时间偏离权威状态或穿墙。

这些规则只影响渲染，不产生任何客户端判定。

## 6. 带宽汇总（30Hz × 3 冗余）

### 6.1 设计估算（重构前的最坏情况推演）

| 项 | 体积/帧 | 带宽 |
|---|---|---|
| 下行 S0 JSON 现状 | 19572 B | 1720 KB/s（不可能）|
| 下行 S2 二进制（未做色块增量） | 1336 B | 117 KB/s = 960 kbps |
| 上行 Fragment | 12 B | 1.05 KB/s（含头 3.5 KB/s）|
| 1Hz 低频通道 | ~600 B | 0.6 KB/s |

### 6.2 实测（2026-09-03，含色块增量与低频拆分）

| 通道 | 均包 | 帧率 | 人均下行 |
|---|---|---|---|
| **UDP / WebTransport 二进制 v1**（公网旧实测，×3 冗余） | 93 B | 31.0 Hz | **10.7 KB/s** |
| **二进制 v3**（含 kind + 移动流星稳定 mid，×3 冗余） | 约 135 B（v2 实测 +6B/帧） | 31.4 Hz | **约 14.8 KB/s** |
| TCP JSON（旧对照：30Hz，deflate 后） | — | 29.9 Hz | 37.8 KB/s |
| TCP JSON 保底（当前：15Hz） | — | 约 15Hz | 约 19 KB/s（待部署实测） |

实测远好于 §6.1 的估算，原因是估算未计入随后落地的**色块增量同步**与
**低频通道拆分**。v3 为连续渲染补回移动流星稳定 mid 后，人均下行仍只约
14.2 KB/s，明显低于 40 KB/s 预算。TCP 保底不享受这两项收益，因此不再跟随加速通道
强行提到 30Hz。

> 因此 **§2.5 主动视野裁剪在 30Hz 下仍不需要做**：常规帧离 1472 的分片线
> 仍有充足余量，`_degradeCount` 在当前公网样本中恒为 0。
> 触发条件与复核结论见 `docs/plan/02-udp-refactor-plan.md` 1a.5b。
>
> 两个旋钮都留着：带宽紧张时 `SNAP_EVERY=2` 立刻减半（客户端延迟自动回 119ms）。

## 7. 边界与已知限制

### 7.1 必须守住的不变量

1. **单个裸 UDP datagram ≤ 1472 字节**，永不触发 IP 分片（§2.6 硬约束兜底）
   > 弱网实测：2% 链路丢包在 14 分片时放大成 **23.9%** 整帧损失（11.7×）
   > WebTransport 还要满足每个 QUIC 会话协商出的 `datagrams.maxDatagramSize`；
   > 最终上限取二者较小值，超出时该帧改走 TCP 全量，不能把 `tooBig` 当发送成功。
2. **上行保持绝对量语义且 seq 跨通道共享**，不得改为增量或为 TCP/加速各自计数
   > 弱网实测（55% 丢包）：绝对角度终态误差 **0 rad**，增量语义累积 **11.9°** 永久偏差
3. **判定权 100% 在服务器**，客户端不上报任何判定结果
4. **TCP 通道全程可用**，任何时刻都能降级
5. **冗余副本必须帧内时间打散**，不得同一时刻连发
   > 突发窗口丢包下打散比同时发高 **+10.2pp**，长卡顿次数减少 **73%**；
   > 均匀丢包下两者完全等价（这是实验设计的自检项，见下）

前四条 + 第五条全部由 `test/net/weaknet.test.js`（18 条断言）量化守护，已接入 `npm test`。
弱网实验的完整数据与方法论见 `docs/plan/02-udp-refactor-plan.md`「弱网验证」章节。

**实验设计要点**：丢包模型必须**时间相关**。若每个包独立以概率 p 丢弃，
则同一帧的 N 个副本各自独立存活，「同时发」与「打散」在数学上完全相同 ——
测试会显示无差异，而结论「打散有用」变成不可证伪的信仰。
因此坏窗口按**到达时刻**判定，并保留均匀丢包作对照组：
若对照组里打散也显示优势，说明模型偏袒了打散、实验无效。

### 7.2 精度取舍（已验证可接受）

| 量 | 编码 | 精度 | 实测影响 |
|---|---|---|---|
| 坐标 | uint16 1px | 1px | 蛇节半径 13px，无感 |
| 头部角度 | uint8 2π/256 | 1.4° | TURN_RATE 下单帧转向远大于此 |
| 节心方向角 | uint8 2π/256 | 1.4° | 累积误差平均 1.38px / 最大 3.68px |
| 上行角度 | uint16 2π/65536 | 0.005° | 远超需要 |

### 7.3 将来若加「一次性技能」必须重新设计

当前所有上行都是**每帧持续重发的绝对量**，所以旧帧数据零价值。
若新增单次点击的技能按钮，那是**不可替代的离散事件**：

- 方案 A：技能事件走 TCP（简单，延迟略高）
- 方案 B：上行 Fragment 额外携带**前 N 帧的技能事件**做补发（低延迟，需去重）

**不可沿用当前「只发当前帧」的策略** —— 这是本设计的显式前提。

#### 7.4.1 WebTransport 现状（2026-09-03 实测确认）

原先文档写「二期评估」，该判断**已过时** —— Safari 26.4（2026-03）补齐最后一块，
WebTransport 进入 Baseline，`caniuse` 全球覆盖 **89.96%**：

| 浏览器 | 支持起始版本 |
|---|---|
| Chrome / Edge | 97（2022） |
| Firefox | 114（2023） |
| Safari / iOS Safari | 26.4（2026-03） |

**已在本项目服务器上跑通完整闭环**（真 QUIC 握手 + Let's Encrypt 证书 + 双向 datagram）：

```
quiche 传输就绪 ✓
[srv] Http3Server ready udp/4443
[srv] session ready ✓
[cli] client.ready ✓
[srv] 收到 datagram: ping-from-client ✓
[cli] 回程 datagram: pong-from-server ✓
```

**关键结论：nginx 不能反代 WebTransport，必须让 Node 直接终结 QUIC/TLS。**

- `ngx_http_v3_module`（1.25+，官方标注 **experimental**）只能做 HTTP/3 的**终端**
- nginx 不通告 `SETTINGS_ENABLE_CONNECT_PROTOCOL` / `SETTINGS_H3_DATAGRAM` /
  `SETTINGS_WT_ENABLED`（draft-ietf-webtrans-http3 §2.2 要求三者齐备，
  浏览器看不到就直接拒绝建会话）
- nginx 主动拒绝 `CONNECT` 方法，也不解析 `:protocol` 伪头
- 更根本的：nginx **没有 HTTP/3 上游能力**，`proxy_pass` 只能走 h1/h2，
  H3 DATAGRAM 无法转发
- **也不能用 `stream{}` 的 UDP 透传**：它按四元组做伪会话，
  QUIC 的 Connection ID 迁移会直接断连（与 §3 UDP 不走 nginx 同源的理由）

因此目标形态是**双端口并存**（互不干扰，nginx 只占 TCP）：

```
443/tcp  → nginx（不动）→ 反代 wss 到 Node    ← 回退路径，始终可用
443/udp  → Node 内 Http3Server 自行终结 QUIC  ← WebTransport
```

其他已核实的事实：

- **证书可直接复用** `/etc/letsencrypt/live/.../fullchain.pem` + `privkey.pem`，
  浏览器走标准 Web PKI，**不需要** `serverCertificateHashes`（那套 14 天有效期
  限制只适用于自签 hashes 路径）。一 TCP 一 UDP，socket 不冲突。
- **`updateCert` 在 HTTP/3 下是 no-op，热换证书不存在**（查源码 + 实测确认）。
  `Http3Server.updateCert` 的实现是 `if (transport.updateCert) transport.updateCert(...)`，
  而该方法**只有 http2 transport 实现了**（走 Node `setSecureContext`）；
  `-transport-http3-quiche` 里全包零命中。条件不成立 ⇒ 静默跳过、不报错，
  **返回 true 只代表调用没炸**。
  证伪方式（唯一可靠的）：换证后用**新**证书 hash 连不上、用**旧**的照样连通。
  ⇒ certbot 续期只能靠**重建端点**（`_watchCert` + `_rebuild`）。
  重建期间在局玩家由 `UdpAccel` 停滞检测自动切回 wss —— **1b 的降级路径
  正好就是换证的缓冲垫**，不需要额外机制，也不必重启进程（那会断掉 WebSocket）。
- **`datagrams.writable` 已被库标注 deprecated**（仍可用，但将来要跟进 API 变化）。
- **`@fails-components/webtransport` 1.6.7 有 linux x64 预编译**，
  实测 `npm install` 18 秒完成，**不需要 cmake/g++**。native 二进制在独立包
  `@fails-components/webtransport-transport-http3-quiche`，必须一并安装。
- **`Alt-Svc` 与 WebTransport 无关** —— 它只让普通 https 请求升级到 h3；
  WebTransport 客户端直接对 URL 里的 `authority:port` 发起 QUIC 连接。
- **WebTransport 目前没有 TCP 回退**（IETF 的 WebTransport over HTTP/2 尚未落地浏览器）。
  UDP 被封的网络下它直接连不上 ⇒ **wss 回退不是可选项，是必需项**。
- **标准 `443/udp` 的穿透性通常优于高位 UDP 端口**。dev 的 `8093/udp` 便于与 official
  的 `443/udp` 进程隔离，但不能据此假设手机 4G 一定可达；遇到“移动网络仍是 WSS”时，
  必须用同一手机测试期间的服务器 `tcpdump` 判定是否有入站 QUIC，并以 `443/udp` 做 A/B。
  仅凭“换成 4G”或“服务端正在监听”都不能证明公网 WebTransport 已打通。

### 7.4.2 浏览器回落诊断契约

客户端诊断状态使用稳定枚举，不依赖错误文案：

- 阶段：`not_attempted / connecting / active / fallback / terminal`
- 建立前：`client_disabled / module_missing / offer_missing / webtransport_unsupported /
  invalid_offer / factory_unavailable / attach_failed`
- 建立中：`constructor_throw / wt_ready_rejected / datagram_api_error /
  hello_ack_timeout`
- 运行中：`socket_error / write_rejected / read_rejected / session_closed /
  downlink_stall / send_failed`

`__net()` 至少显示：`WebTransport支持`、`安全上下文`、`加速状态`、`加速失败阶段`、
`加速失败原因`、`加速目标`、`Socket错误`。首次握手从未成功也必须留下失败原因，不能因为
`fallbacks` 只统计“active → false”而显示成“降级 0 次、原因未知”。错误摘要只保存在本机
诊断中，不向服务端发送 token、证书或堆栈。

### 7.5 服务器侧前置条件

- 出网 MTU 已确认 1500
- `net.core.rmem_max` 当前 212992（默认值），高频 UDP 需调大
- UDP 端口需在**两层**放行：服务器 ufw + 云轻量控制台（后者只能手动操作）
